# Frontend modernization: Nuxt, civic UI, SEO, and hosting

Status: completed; Nuxt is production on Cloudflare Workers, automated releases
are active, and the former Netlify project is stopped and repository-unlinked
Original plan: 2026-08-15; production cutover: 2026-08-18

The document below preserves the decisions and gates used during migration.
Future-tense and “current Netlify” language in the phase plan describes the
historical state at that gate; it is not the live topology. Use `README.md`,
`frontend/README.md`, and the cutover runbook for current operations.

## Decision summary

**Unbreakable migration principle: simpler is better.** At every design and
implementation decision, ask whether the result can be simpler. If it can,
simplify it. Add a component, abstraction, dependency, server boundary, or
deployment service only when the current product needs it and the simpler
alternative is inadequate.

Parity comes before enhancement. During the migration, a slice may redesign
presentation for clarity or accessibility only while preserving the legacy
capability and semantics. New filters, analyses, derived views, and workflows
wait until explorer parity and require a separate product decision.

Migrate the frontend to Nuxt 4 in small, reversible slices. Keep the existing
Vue/Vite application runnable until the Nuxt version reaches feature parity.
Use Nuxt's default server rendering for meaningful page content, while loading
MapLibre and other browser-only analytics code on the client.

Build the new visual system as a local Nuxt Layer named `civic-ui`, backed by
the real `@uswds/uswds` packages, Sass theme settings, component markup, and
accessibility guidance. Use Public Sans for body, heading, and interface roles.
Preserve the dashboard's charcoal background and red/yellow map-and-data
semantics as the project identity. Do not add the federal banner, seal, or
default federal presentation. The current About and Statistics treatment is a
migration reference, not the target design.

Deploy the production Nuxt application to Cloudflare Workers with Workers
Assets after a measured staging trial. Keep FastAPI on Fly.io during the
frontend migration. Revisit the API host only after the frontend cutover is
stable and its actual cost and traffic are known.

This is deliberately both a product migration and a Nuxt learning project.
Each phase introduces a small set of Nuxt concepts and leaves behind a working
vertical slice.

## Why this direction fits this repository

The current application has several assets worth preserving:

- content-addressed, year-specific NDJSON endpoints with strong browser caching;
- a mature MapLibre/D3/Arquero interaction model;
- accessibility, browser, Lighthouse, and bundle-budget tests;
- a distinctive charcoal, red, and yellow dashboard identity worth preserving;
- a FastAPI service that already computes and caches authoritative statistics.

The main constraints are also clear:

- the Vite SPA does not render its useful page content in the initial HTML;
- crawler content is split between hidden build-time summaries and an HTML page
  generated by the API;
- Vuetify owns important controls and theme variables, and scoped CSS reaches
  into Vuetify internals;
- MapLibre and some D3 code use browser APIs and cannot run during SSR;
- the canonical site currently lives below
  `/philly-gun-violence-map`, so URL continuity matters during a host change.

Nuxt directly addresses routing, server rendering, metadata, server endpoints,
code splitting, and hybrid rendering without giving up Vue. A Nuxt Layer is a
natural first home for the reusable civic grammar because layers can share
components, composables, utilities, layouts, and configuration while remaining
local to the application.

## Target rendering model

SSR should render information people and crawlers can understand. It should not
attempt to render the map on the server.

| Surface | Initial response | Hydrated behavior |
| --- | --- | --- |
| Dashboard | Title, current summary, data-through date, methodology link, filter labels, map description, noscript/download path | Filters, MapLibre map, charts, URL state, downloads |
| Statistics | Full current figures, year table, interpretation, definitions, and sources | Optional enhancements only; core page works without JavaScript |
| About | Full project purpose, ownership, appropriate use, and correction path | Ordinary navigation |
| Methodology/data pages | Full visible HTML | Little or no client JavaScript |
| Map canvas | Stable accessible fallback inside `ClientOnly` | MapLibre, search, layers, tooltips |
| Charts | SSR summary/table equivalent | D3 charts and synchronized filtering |

The dashboard's large immutable NDJSON files should continue to go directly
from the browser to the FastAPI/data origin. Sending those payloads through the
Nuxt renderer would add cost and remove the value of the existing cache keys.
Nuxt should fetch only small summary and freshness payloads on the server.

Suggested route rules, to be validated against the selected Cloudflare preset:

```ts
export default defineNuxtConfig({
  routeRules: {
    "/": { swr: 900 },
    "/stats": { swr: 900 },
    "/about": { swr: 3600 },
    "/methodology": { prerender: true },
  },
});
```

The exact cache mechanism is a deployment spike, not an assumption. Tests must
confirm response headers, cache hits, data freshness, and stale behavior on the
real staging target.

## The civic grammar

Treat the design system as a grammar, not a catalog of decorative components.
Each layer combines a small vocabulary into more meaningful structures.

### 1. Foundations: the alphabet

- semantic color roles: canvas, surface, ink, muted ink, rule, link, focus,
  fatal, nonfatal, and data-series colors;
- Public Sans assigned to USWDS body, heading, and UI roles, with tabular
  numerals for data;
- USWDS spacing, measure, grid, breakpoint, border, focus, and motion tokens;
- content rules for dates, uncertainty, sources, freshness, and preliminary data.

Tokens describe purpose, not a specific page. For example, use
`--civic-color-ink-muted`, not `--about-subtitle-gray`.

### 2. Primitives: words

Start with the USWDS components needed to replace Vuetify:

- button, link, icon, and loading/status treatment;
- label, fieldset, select, checkbox, radio, range, and input groups;
- accordion, modal, alert, summary box, and table;
- USWDS grid and spacing utilities.

Use the official `.usa-*` HTML structure and compile only the component packages
the project needs. Add thin Vue wrappers only where reactive bindings, emitted
events, or Nuxt lifecycle handling provide real value. Do not rebuild a parallel
look-alike component library, and do not adopt another themed UI kit in place of
Vuetify.

USWDS's stylesheet, JavaScript library, and initializer are designed as a set.
Content-only components can use the HTML/CSS foundation directly. Interactive
components need a small Nuxt integration spike: load USWDS behavior in a
client-only plugin, reinitialize it after client-side route changes, and verify
that its DOM enhancement does not conflict with Vue hydration or component
cleanup. If a specific USWDS JavaScript behavior cannot coexist cleanly with
Vue, retain its official markup, styling, and accessibility contract while
implementing that behavior in a focused Vue wrapper.

### 3. Patterns: phrases

- restrained page intro, statistical lede, and definition list;
- source register, freshness line, and USWDS data table;
- filter group, download options, and map legend;
- USWDS alert or summary box for caveats, errors, and preliminary-data language.

Patterns include content and accessibility guidance, not only CSS.

### 4. Compositions: sentences

- `CivicContentLayout` for About, Statistics, and Methodology;
- `CivicExplorerLayout` for map-plus-filter analytical tools;
- `DatasetSummary`, `MapExplorer`, `ChartDashboard`, and `DownloadDialog`.

### 5. Page recipes: complete statements

Page recipes define which patterns are required, their order, their semantic
heading structure, and what survives without JavaScript. A page should be able
to vary its voice and data without inventing a new layout system.

Keep `civic-ui` local until a second real civic product uses it. That second
consumer will reveal which abstractions are genuinely reusable; only then
consider publishing it as a package or remote layer.

## Visual direction: USWDS foundation, Philadelphia dashboard identity

Use USWDS as the actual foundation, not just as inspiration:

- install `@uswds/uswds` as a project dependency;
- configure the system through `_uswds-theme.scss` and compile its Sass;
- set the sans family token to `public-sans` and assign it to body, heading, and
  UI roles;
- start with official component packages and `.usa-*` markup;
- use USWDS tokens, utilities, grid, focus treatment, and component guidance;
- include only the packages used by the application to keep the CSS and
  JavaScript footprint controlled.

Keep the ownership boundary explicit:

| Layer | Owns |
| --- | --- |
| USWDS | Component structure, base behavior, accessibility guidance, tokens, typography scale, grid, utilities |
| `civic-ui` | Dark theme settings, Public Sans roles, Philadelphia data colors, Nuxt integration, shared civic-analytics compositions |
| Application | Gun-violence terminology, data contracts, map/chart behavior, page content, and route-specific decisions |

The USWDS showcase is evidence that a shared foundation can support many
different brands and information architectures. Use those sites to study how
teams compose and customize the system, not as visual templates to reproduce.

The brand layer sits on top of that foundation:

- page canvas remains charcoal (`#353d42` or a contrast-tested refinement);
- white and warm gray text provide the main hierarchy;
- red remains reserved for fatal shootings and genuine errors;
- yellow remains reserved for nonfatal shootings and its established map/data
  meaning;
- other visualization colors remain quiet and colorblind-safe;
- Public Sans carries prose, headings, labels, controls, and figures, using
  tabular numerals where values must align;
- rules, spacing, alignment, and type weight create hierarchy before boxes,
  fills, icons, or ornament.

This is a custom dark USWDS theme, not a federal-site simulation. Do not use the
official-government banner, seal, flag treatment, agency masthead, or default
federal blue simply to signal legitimacy. It should feel like an independent
Philadelphia civic data product built from a mature public-service design
system.

### Restraint rules for content pages

The current About and Statistics pages feel flashy because several attention
devices compete at once: oversized centered heroes, widely letterspaced all-caps
labels, numbered section treatments, icon or emoji decoration, symmetrical KPI
bands, and repeated accent colors. Removing Vuetify alone would not fix that.

About, Statistics, Methodology, and Data should keep the charcoal canvas while
using a quieter content grammar:

- one left-aligned H1 and short introduction;
- sentence-case H2 headings at a modest size;
- ordinary USWDS spacing and a readable `usa-prose` measure;
- simple rules between major sections where needed;
- no decorative emojis, numbered section rails, gradient chips, hover lifts,
  or icons beside every heading;
- no all-caps text except short functional labels where USWDS guidance supports
  it, and no exaggerated letterspacing;
- use cards, alerts, summary boxes, and colored surfaces only when their
  component meaning is useful;
- use red and yellow only for their data semantics, never as general decoration.

Civic character should come from component consistency, accessibility, source
provenance, visible update dates, definitions, limitations, and plain language.

## About and Statistics redesign brief

The content pages should be redesigned during the Nuxt migration rather than
ported pixel-for-pixel. Their shared frame should use a restrained project
masthead built from the USWDS header and navigation patterns, a USWDS grid
container, a readable `usa-prose` measure, Public Sans, and the dashboard's dark
theme. A small link to `nickhand.dev` can establish ownership without making
these pages visually copy the homepage.

### About: from project biography to public accountability

Working page title: **About this project**

Working lead:

> An independently maintained public record of shootings in Philadelphia,
> built to make official data easier to understand, explore, and use.

Immediately identify ownership and status:

> Built and maintained by Nick Hand in Philadelphia. This is an independent
> project, not an official City of Philadelphia website.

Recommended content order:

1. **Why this exists** — a short first-person account of the public need and why
   the project continues. Avoid the current third-person biography.
2. **What the dashboard shows** — shooting victims, fatal/nonfatal outcome,
   geography, time, demographics, and automated public-court-search results;
   distinguish victim records from incidents.
3. **Where the data comes from** — a source register with publisher, dataset,
   coverage, update schedule, data-through date, and source link.
4. **How the data moves** — a plain-language pipeline: public source → automated
   checks and transformations → versioned data → map, charts, and downloads.
5. **What the data cannot tell you** — preliminary status, revisions,
   officer-involved-shooting exclusion, court-search uncertainty, homicide-count
   differences, missing fields, and the limits of point locations.
6. **Stewardship and corrections** — who maintains the project, how issues are
   corrected, source/code links, and a direct contact path.

The page should offer visible routes back to the explorer, current statistics,
downloads, methodology, and source code. Technology details such as Vue,
FastAPI, or Nuxt belong in the repository or a small implementation note, not as
a primary reason for public trust.

Useful USWDS components for this page:

- `usa-prose` for primary reading content;
- a restrained `usa-summary-box` for independent ownership and data status;
- `usa-table usa-table--borderless usa-table--stacked` for the source register;
- `usa-process-list` for the data pipeline;
- `usa-alert` only for a limitation or correction that requires special
  attention;
- ordinary `usa-button` links for Explore, Download data, and View source.

### Statistics: from KPI report to an explained current picture

Working page title: **Philadelphia gun violence: current data**

The first viewport should answer three questions in plain language:

- What period does this cover?
- How many people were shot, and how many shootings were fatal?
- How does the same period compare with last year?

Use a left-aligned statistical lede instead of three centered KPI columns.
Public Sans should carry both figures and interpretation, with tabular numerals,
weight, and the USWDS type scale providing hierarchy. Every comparison must
state whether it is year-to-date or a full calendar year.

Recommended content order:

1. **Current picture** — an editorial lede with current totals, fatal/nonfatal
   split, the exact data-through date, and a same-period comparison.
2. **How this year compares** — a simple annotated time series or paired
   comparison, plus a semantic table. Do not rely on color alone.
3. **The longer view** — annual victims and homicides with the peak, recent
   direction, and honest cautions about comparing an incomplete year.
4. **Two measures, different meanings** — explain why shooting victims and PPD
   homicide totals are not subsets of one another.
5. **Definitions and notes** — concise answers to real interpretation questions,
   replacing SEO-shaped repetition and the generic FAQ block.
6. **Use the data** — links to the filtered explorer, CSV/GeoJSON, API
   documentation, methodology, source datasets, and code.

The existing year table is useful and should remain semantic, but the design can
make one trend visually dominant and treat the table as the exact accessible
record. The current sentences repeat the same totals several times; consolidate
them so each number appears where it adds a new interpretation.

Useful USWDS components for this page:

- USWDS grid utilities for a restrained lede and comparison layout;
- `usa-prose` for interpretation and definitions;
- `usa-table usa-table--compact usa-table--borderless` inside a scrollable
  container for exact annual values;
- `usa-summary-box` for the distinction between shooting-victim and homicide
  measures;
- `usa-button-group` for Explore the map and Download data;
- a USWDS-compliant data visualization palette customized around the existing
  red/yellow semantics.

### Shared writing rules

- write in first person where ownership matters and plain institutional voice
  where defining data;
- prefer “people shot” or “shooting victims” according to the source measure,
  and define the choice;
- put the date or period beside every current total;
- state uncertainty next to the affected measure, not only in a footer;
- name the publisher and dataset rather than saying “public data” generically;
- distinguish source facts, derived calculations, and interpretation;
- avoid promotional claims such as “modern tools” unless they help someone use
  or evaluate the data;
- never add prose solely to target a keyword or structured-data field.

## SEO and crawler discoverability

SEO is primarily a content and rendering concern here. The migration should
remove hidden crawler-only summaries and make the same useful information
visible to everyone in server-rendered HTML.

### Required technical baseline

- one canonical URL and unique title/description for every indexable page;
- server-rendered headings, summaries, links, tables, source attribution, and
  data-through dates;
- `sitemap.xml` with canonical content routes; add `lastmod` only from an
  authoritative page-publication timestamp, not a data-through date;
- `robots.txt` with the sitemap location and explicit policy for search and AI
  crawlers;
- Open Graph and X cards with absolute URLs;
- structured data derived from the same records rendered on the page;
- permanent redirects for every existing public URL and no canonical split
  between Netlify, Fly.io, and the public site;
- crawlable internal links instead of navigation that exists only after
  hydration;
- correct 404 status and metadata;
- Core Web Vitals budgets and no MapLibre code on content-only routes.

Use Nuxt's `useSeoMeta`/`useHead` for page metadata. Use the maintained Nuxt
sitemap module rather than hand-building XML. Keep the robots policy static
while the application is mounted below a non-root base path.

### Content model

Initial indexable pages should be useful on their own:

1. `/` — current summary plus the interactive dashboard;
2. `/stats` — current figures, year table, trends, definitions, and notes;
3. `/about` — ownership, history, sources, and contact;
4. `/methodology` — definitions, transformations, matching, limitations, and
   update cadence;
5. `/data` — download formats, API entry points, licensing/provenance, and field
   documentation.

After the first launch, add year pages such as `/stats/2025` only when each page
has genuinely distinct, useful content: annual totals, outcome breakdowns,
context, source dates, and links to the matching filtered view. Do not generate
thin neighborhood or query-combination pages merely to create more URLs.

Recommended structured data:

- `Dataset` with spatial coverage, temporal coverage, source provenance, and
  distributions; include `dateModified` only when an authoritative processing
  timestamp is available;
- `WebSite` and `WebPage` relationships;
- `SoftwareApplication` or `WebApplication` for the explorer;
- `FAQPage` only for questions visibly rendered on the page.

Structured data must never contain fresher or different values than the visible
page. It helps machines understand the page; it does not substitute for strong
HTML, links, and content.

### SEO acceptance checks

- `curl` of each indexable URL contains its H1, primary copy, current dates, and
  internal links without executing JavaScript;
- JavaScript-disabled browser tests can read About, Statistics, Methodology, and
  Data pages and can reach a download/API path from the dashboard;
- canonical, Open Graph, JSON-LD, sitemap, robots, redirects, and 404s are
  covered by automated tests;
- Google Rich Results/schema validation has no errors for supported types;
- Lighthouse SEO, accessibility, and performance thresholds remain enforced;
- the client console has no hydration mismatch warnings;
- the map bundle is absent from content-only route chunks.

## Nuxt learning path

Each implementation phase should include a short README note answering: what
Nuxt did, what would have been manual in Vite, what ran on the server, what ran
in the browser, and how the behavior was tested.

| Phase | Product slice | Nuxt concepts learned |
| --- | --- | --- |
| 1 | Nuxt shell plus redesigned About page | `app.vue`, file routes, layouts, auto-imports, components, CSS/assets, `NuxtLink`, DevTools |
| 2 | SSR Statistics page fed by a typed summary endpoint | universal rendering, hydration, `useAsyncData`, `$fetch`, runtime config, errors, server/client execution |
| 3 | SEO and content routes | `useSeoMeta`, `useHead`, route metadata, server routes, sitemap/robots/schema modules, route rules |
| 4 | Dashboard shell, year control, and point map | shared composables, SSR query state, progressive enhancement, client-only components |
| 5 | Map and D3 port | `.client` components/plugins, `ClientOnly`, lazy hydration, code splitting, lifecycle cleanup |
| 6 | Cloudflare staging | Nitro presets, Worker runtime, assets, environment variables, cache headers, observability |
| 7 | Reusable civic layer | layer priority, `app.config`, overrides, module boundaries, documentation |

Avoid teaching every Nuxt feature at once. Middleware, Nuxt Content, database
bindings, authentication, and experimental islands should be introduced only
when a real requirement calls for them.

## Migration phases and gates

### Phase 0: baseline and contracts

- Record current screenshots, accessibility results, bundle budgets, routes,
  query parameters, API requests, and SEO output.
- Add an architecture decision record for Nuxt/SSR and one for hosting.
- Define the typed statistics-summary contract in FastAPI.

Gate: legacy build and all current tests remain green.

### Phase 1: parallel Nuxt foundation

- Add Nuxt 4 alongside the current Vite entry point.
- Create the local `layers/civic-ui` layer with selected USWDS packages, Public
  Sans, dark theme settings, project color tokens, and the first content layout.
- Redesign and port About first because it exercises content design, layout,
  data fetching, metadata, and responsive behavior without MapLibre risk.

Gate: the Nuxt About page clearly uses the customized USWDS system, retains the
dashboard's visual identity without flashy ornament, renders the complete
public-accountability content in server HTML, and passes content, accessibility,
and responsive review.

### Phase 2: authoritative SSR statistics

- Expose the existing `StatsSnapshot` as a small typed JSON endpoint while
  retaining the current FastAPI HTML page as a rollback path.
- Redesign Statistics around a current-picture lede, meaningful comparisons,
  definitions, and the exact table, all from that authoritative snapshot.
- Move sitemap and structured-data ownership to Nuxt only after parity.

Gate: visible figures, HTML, JSON-LD, sitemap entries, and API values agree in an
automated test. The page remains useful with JavaScript disabled.

### Phase 3: content routes and crawler infrastructure

- Add server-rendered Methodology and Data pages using the shared civic layout
  and source-freshness metadata.
- Move canonical metadata, structured data, sitemap generation, robots policy,
  and the 404 response into the Nuxt target.
- Verify raw HTTP responses against deterministic API fixtures without relying
  on client-side JavaScript.

Gate: About, Statistics, Methodology, Data, sitemap, robots, and missing routes
pass the raw SSR crawler suite; visible Statistics values agree with the API and
structured data.

### Phase 4: dashboard shell and Vuetify replacement

The first Phase 4 slice establishes the root route before moving the full
explorer. It reuses one typed `useStatsSnapshot` composable with the Statistics
page, renders current figures and source dates during SSR, and provides a
native `GET` year control that works without JavaScript. Year queries describe
views of the same dashboard, so their canonical remains the queryless root.

When the snapshot is unavailable, the shell keeps its explanatory content and
data/method links, labels live values as unavailable, and never presents
missing values as zero.

The browser-only explorer fetches `/shootings/meta`, follows its versioned
NDJSON URL for one selected year, and follows every dated feed for All Years.
It commits the All Years view only after every feed succeeds and retries the
manifest plus rows once after a stale version. MapLibre remains lazy; detailed
records never enter SSR or its hydration payload.

The SSR fallback reserves the production map-and-sidebar footprint. A validated
`map=zoom/latitude/longitude` value now restores the initial
viewport; map movement replaces that rounded URL state without introducing
Pinia or adding a history entry for every pan. The native filter form deliberately resets the
viewport. The existing `layers` grammar now supports point, density heat-map,
street-block hot spots, and the seven mutually exclusive boundary aggregations.
The city outline remains a static reference. Point hover and pinned click use a
restrained MapLibre popup with normalized date, time, location, demographic,
incident-number, and court-search-result fields. It avoids the legacy raw-HTML tooltip
builder and preserves the nearest-street caveat.
The client explorer now owns the selected-view rows once and ports the legacy
Fatal shootings only, Court search returned a result, Gender, Race/Ethnicity, Day of
Week, Time of Day, Date, and Age filters. Category filters retain the legacy
individual checkbox, “only,” and reset behavior. Each histogram excludes its
own range while respecting every other active filter; Age retains “Exclude
unknown values.” Filter changes update the existing GeoJSON source without a
second year request or Pinia. The same rows now feed the five legacy view-only
category charts, filtered/full CSV and GeoJSON downloads, address-search
context, and on-demand street or boundary overlays. Raw downloads retain
unmapped records; aggregate GeoJSON fetches only its selected boundary geometry.
Changing only the map query through browser navigation repositions the existing
map instance without another manifest or year-data request.

- Port navigation, header, filters, loading/error states, download dialog, and
  footer using `civic-ui` primitives and patterns.
- Reuse current API contracts where they are universal-safe. Do not carry Pinia
  into Nuxt by default; use URL state and small composables until shared
  explorer complexity demonstrates a store is simpler.
- Preserve the legacy state boundary for the first filter ports: Arquero/filter
  and histogram state is local today, while Pinia owns longer-lived datasets.
  The client explorer parent now loads one selected view once and shares it with
  the map and all record filters without adding a global store.
- Replace Vuetify one widget family at a time: buttons/icons, selection inputs,
  disclosures, sliders, then dialogs/loading.

Gate: no Vuetify imports, theme variables, deep selectors, or test plugins
remain. Keyboard, focus, touch, error, and high-contrast behaviors have parity.

### Phase 5: browser-only analytics

- The client-only explorer owns the selected-view rows once and shares them
  with map layers, filters, five category charts, and downloads.
- Native Vue/HTML/CSS category bars preserve the legacy view-only breakdowns
  without adding another chart lifecycle or state library.
- Address lookup, boundary geometry, and filtered street segments load only
  when their controls request them. A failure in one supplement does not erase
  the selected-view summary or other tools.
- Keep an SSR map description, summary, and data link as the fallback.
- Verify event cleanup and route navigation because Nuxt can remount pages
  differently from the current keep-alive shell.

Gate: filters, URL state, lazy year loading, map layers, charts, address search,
downloads, and back/forward navigation pass end-to-end tests. Content routes do
not download MapLibre.

### Phase 6: deployment canary and SEO cutover

The repository now has a local-only Cloudflare staging target. Running
`npm run build:nuxt:cloudflare` selects Nitro's `cloudflare_module` preset and
then checks the Worker entry, base-prefixed Workers Assets, explicit Wrangler
configuration, observability, and crawler exclusion. The staging Wrangler file
has no route or custom domain, and the repository has no deploy command. This
proves build compatibility without granting a build the ability to change
traffic.

- Deploy a staging Worker with Workers Assets and observability enabled.
- Test CPU time, cache hit rate, origin fetches, 5xx behavior, data freshness,
  custom-domain routing, and rollback.
- Crawl staging and compare rendered HTML, redirects, canonicals, sitemap, and
  link graph with production.
- Preserve public paths or add one-hop permanent redirects before changing the
  canonical host.

The canary must stay non-indexable through both HTML robots metadata and the
`X-Robots-Tag` response header. Production remains indexable. Cutover is one
explicit routing change only after the canary gate passes; it does not move the
FastAPI service or data pipeline. Rollback means returning that route to the
legacy Netlify deployment while leaving the API untouched. Netlify's legacy
SSR/SEO proxies, status-200 SPA fallback, and the host-root robots/sitemap
references change only as part of the final cutover, not during staging.

Gate: at least one week of stable canary behavior, explicit rollback steps, and
no SEO URL loss. Then switch traffic and keep the legacy deployment available
for a short rollback window.

### Phase 7: extraction only after reuse

- Use the layer in a second civic analytics page or application.
- Move only proven reusable components into a separately versioned package or
  remote layer.

Gate: application-specific data assumptions do not leak into `civic-ui`.

## Hosting recommendation

### Recommended target: Cloudflare Workers with Workers Assets

Why:

- Nuxt has an official Cloudflare Worker deployment path;
- static asset requests are free and unlimited, while only SSR/Worker requests
  consume Worker usage;
- the Worker and static assets deploy as one versioned unit;
- a paid Workers account has a predictable low base price and higher CPU limits;
- custom CPU limits and observability help control runaway cost and failures.

As of 2026-08-14, Cloudflare documents a free Worker tier of 100,000 requests per
day with 10 ms CPU per invocation. The paid plan starts at $5/month and includes
10 million requests and 30 million CPU milliseconds per month. Cloudflare notes
that SSR commonly uses more CPU than simple Workers, so production should be
budgeted against the paid tier rather than assuming the free tier is sufficient.

Do not move the FastAPI/data service during the Nuxt cutover. The API is a
separate reliability domain with S3 loading, scheduled refresh, court data, and
large payload behavior. Optimizing it deserves its own measured decision after
the user-facing migration.

### Why not decide from platform price alone

The current Netlify frontend is static and uses redirects rather than Netlify
Functions, so it may already be inexpensive. Nuxt SSR changes the usage shape.
Before cutover, compare 30 days of:

- requests and bandwidth by static asset versus HTML render;
- build frequency and duration;
- Worker/function CPU and error rate;
- origin calls to Fly.io;
- current Netlify and Fly.io invoices;
- recovery time from a bad deploy or API outage.

Netlify remains a valid fallback because Nuxt supports it well, but its current
credit model charges across production deploys, compute, and bandwidth. Vercel
is operationally easy, but its paid baseline and usage model are less attractive
for this independent civic project unless its Nuxt integration materially lowers
maintenance. Self-hosting a Node SSR server would offer control but create more
patching, scaling, and failover work than this site needs.

## Reliability requirements

- immutable, content-hashed client assets with long cache lifetimes;
- short-cache or stale-while-revalidate HTML and small summary data;
- stale-on-origin-error behavior for public statistics where technically
  possible, with an honest visible data-through date;
- health monitoring for the Nuxt renderer and FastAPI origin;
- deploy previews, atomic production deploys, and a documented rollback command;
- error budgets and alerts based on user-visible failures, not only process
  uptime;
- no frontend deploy required for routine daily data freshness;
- secrets only in platform runtime configuration, never public Nuxt config.

## Explicit non-goals for the first migration

- rewriting the Python API or ETL system in TypeScript;
- proxying large NDJSON datasets through Nuxt;
- replacing Pinia, Arquero, D3, or MapLibre without a measured reason;
- publishing `civic-ui` before a second consumer exists;
- shipping unused USWDS component packages or reproducing a federal website;
- generating large numbers of thin SEO pages;
- changing the public URL structure during the same release as the framework
  cutover unless the redirect plan is independently verified.
